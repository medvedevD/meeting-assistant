# Resume In-Flight Jobs On Restart

**Status:** Backlog

## Context

Если закрыть приложение во время транскрипции или генерации протокола, jobs
живут в SQLite на стороне бэкенда (см. Этап 2 в
[.claude/plans/rust-tauri-rewrite.md](../.claude/plans/rust-tauri-rewrite.md)),
но QML‑слой при следующем запуске нигде их не подсвечивает. Пользователю не
видно, что у какой‑то встречи была незавершённая работа, и нельзя продолжить
наблюдение за прогрессом.

Важно: **фактическое возобновление обработки на бэкенде уже работает.** При
старте воркера вызывается reconcile
([worker.rs:84-89](../rust/crates/adapters/src/worker.rs#L84-L89)):
`recover_running_jobs` сбрасывает `running → pending`
([job_repo.rs:32-36](../rust/crates/core/src/ports/job_repo.rs#L32-L36)), и цикл
переподхватывает их штатным `claim_pending`. Прерванный рестартом job
**не падает**, он дорабатывается заново. Недостаёт двух вещей:

1. **Эндпоинта перечисления активных jobs** — сейчас на бэкенде есть только
   `POST /api/v1/jobs` и `GET /api/v1/jobs/:id`
   ([router.rs:140-141](../rust/crates/api/src/router.rs#L140-L141)); способа
   спросить «что сейчас в работе» нет.
2. **UI‑видимости** — засеять `ActiveJobsStore` после рестарта и показать
   счётчик активных jobs в сайдбаре.

В Python‑версии (Этап 2/5 плана meeting‑pipeline‑redesign) у нас уже был
reconcile при старте и queue‑badge в сайдбаре — этот UX нужно повторить в
Rust/Qt стеке.

## Goal

После перезапуска приложения активные / ожидающие jobs видны пользователю,
прогресс по конкретной встрече подхватывается автоматически. Появляется единая
точка, где видно «что сейчас обрабатывается».

## Scope

**В этой задаче:**
- Бэкенд: эндпоинт перечисления активных jobs + опорный метод репозитория.
- QML: засев `ActiveJobsStore` активными jobs при `api.configured`.
- Сайдбар `AppShell`: счётчик активных jobs; клик — список встреч в работе.
- Индикатор «в работе» в строке встречи в сайдбаре уже покрыт
  [active-jobs-store.md](active-jobs-store.md); здесь он лишь начинает
  отображаться и для восстановленных после рестарта jobs.

**Вне этой задачи:**
- Сам стор, долгоживущие `JobPoller`, рендер `PipelineProgress` из стора,
  терминальный TTL — `active-jobs-store.md` (база, поверх которой строится
  эта задача).
- Перевод транскрипции на job‑механизм — `transcription-progress-visibility.md`
  (выполнено).

## Decisions

1. **Форма эндпоинта — `GET /api/v1/active-jobs`** (отдельный узкий маршрут, не
   `GET /api/v1/jobs?status=...`).
   - *Почему:* в кодовой базе нет ни одного list‑маршрута для jobs, и под
     единственный сценарий «что сейчас в работе» отдельный эндпоинт проще:
     никакого парсинга/валидации `?status=`, никакого преждевременного
     обобщения на историю/фильтры (YAGNI). Если позже понадобится history/failed
     с фильтром — расширим тогда.
   - *Статус:* рекомендация, ревизуемо. Если хочется заранее заложить
     универсальный list — переключиться на `?status=pending,running` без потерь
     для QML‑стороны (меняется только URL).

2. **Скоуп статусов — только in‑flight (`pending` + `running`).** Failed‑while‑
   closed в эту задачу не входит.
   - *Почему:* благодаря reconcile единственные jobs, оставшиеся `failed` после
     закрытия, — это исчерпавшие 5 попыток ещё до закрытия; они редки и видны
     при открытии встречи как экран ошибки. Терминальные `done/failed` *внутри
     сессии* уже покрывает терминальный TTL `ActiveJobsStore`. Совпадает с
     заголовком задачи «in‑flight».
   - *Статус:* рекомендация, ревизуемо.

3. **Клик по счётчику в сайдбаре — открывает список встреч в работе.** Клик по
   встрече в списке ведёт на её детали (по аналогии с queue‑badge из Python).

## Backend

### Эндпоинт

`GET /api/v1/active-jobs` → `200 [JobResponse, ...]`, где `JobResponse` — тот же
тип, что уже отдаёт `GET /jobs/:id`
([jobs.rs:21-52](../rust/crates/api/src/routes/jobs.rs#L21-L52)):
`{ id, meeting_id, kind, status, attempts, last_error, error_class, progress,
created_at, updated_at }`.

- Поле `progress` (live, из `LiveProgress` DashMap) мёрджится так же, как в
  `status` ([jobs.rs:70-85](../rust/crates/api/src/routes/jobs.rs#L70-L85)).
  После рестарта live‑прогресс пуст, поэтому у только что восстановленных jobs
  `progress == null` — QML дотягивает свежий прогресс штатным поллингом
  `GET /jobs/:id` (его уже поднимает стор через `track`).
- Сортировка: по `created_at` (детерминированный порядок для списка/бейджа).

### Репозиторий

Новый метод в порту
[JobRepo](../rust/crates/core/src/ports/job_repo.rs):
`async fn list_active(&self) -> Result<Vec<Job>, CoreError>` — возвращает jobs со
статусом `pending` или `running`.
- Реализация в [db/job_repo.rs](../rust/crates/adapters/src/db/job_repo.rs)
  (`SELECT ... WHERE status IN ('pending','running') ORDER BY created_at`).
- Реализация в [fakes.rs](../rust/crates/core/src/fakes.rs) для тестов.

### Регистрация и контракт

- Маршрут в `api_routes()`
  ([router.rs:138-150](../rust/crates/api/src/router.rs#L138-L150)):
  `.route("/api/v1/active-jobs", get(jobs::active))`.
- Хендлер `jobs::active` рядом с `jobs::status`.
- Обновить sidecar‑контракт
  ([sidecar_contract.rs](../rust/crates/app/tests/sidecar_contract.rs)) и
  список маршрутов в тесте router’а
  ([router.rs:350-351](../rust/crates/api/src/router.rs#L350-L351)).

## QML

### Засев стора при старте

При `api.configured` (там же, где другие стартовые запросы) — один раз
запросить `GET /api/v1/active-jobs` и для каждого элемента вызвать
`ActiveJobsStore.track(meeting_id, job_id, kind)`
([active-jobs-store.md](active-jobs-store.md) — Store API). Дальше всё работает
через тот же механизм: стор поднимает по `JobPoller` на каждый job, индикаторы и
`PipelineProgress` подхватываются автоматически.

- Идемпотентность: повторный засев (если `api.configured` сработает снова) не
  должен плодить второй поллер на тот же `jobId` — `track` уже заменяет запись
  встречи (инвариант «не более одной активной записи на встречу»).
- Если эндпоинт вернул `running`, а в DB после reconcile там `pending` — это
  один и тот же активный набор; стор не различает их для индикатора (`isActive`).

### Сайдбар: счётчик + список

- В сайдбаре `AppShell` показать счётчик активных jobs, биндинг —
  `ActiveJobsStore.activeCount()`
  ([active-jobs-store.md](active-jobs-store.md) — Store API). Бейдж скрыт при 0.
- Клик по счётчику — раскрывает список встреч с активной работой (имя встречи +
  вид/стадия job‑а). Клик по строке — навигация на детали этой встречи.
- Источник списка — карта `ActiveJobsStore` (meetingId → entry); имена встреч —
  из уже загруженной модели встреч сайдбара.

## Functional Requirements

1. `GET /api/v1/active-jobs` возвращает ровно jobs со статусом `pending` или
   `running`, в форме `JobResponse`, отсортированные по `created_at`.
2. При `api.configured` QML засевает `ActiveJobsStore` всеми активными jobs; для
   каждого поднимается ровно один `JobPoller` (инвариант стора).
3. После рестарта во время обработки: встреча видна в сайдбаре как «в работе»,
   при открытии её деталей виден `PipelineProgress` с процентом/подстадией, как
   только подтянется живой прогресс с бэкенда.
4. Счётчик в сайдбаре равен числу незавершённых jobs и обновляется по мере их
   завершения; при 0 — скрыт.
5. Клик по счётчику открывает список встреч в работе; клик по встрече ведёт на её
   детали.
6. Повторный засев не создаёт дублирующих поллеров на тот же `jobId`.

## Edge Cases

- **Reconcile уже сбросил `running → pending`** к моменту запроса — такие jobs
  входят в выдачу (статус `pending`), стор их отслеживает наравне.
- **`progress == null` после рестарта** — индикатор «в работе» виден сразу
  (по факту наличия записи), процент появляется после первого ответа поллера.
- **Встреча для job‑а удалена** — `list_active` всё равно может вернуть job до
  того, как воркер пометит его `meeting not found`
  ([worker.rs:120-137](../rust/crates/adapters/src/worker.rs#L120-L137)); QML не
  должен падать, если встречи нет в модели сайдбара (строка списка пропускается).
- **`api` не сконфигурирован** — засев не выполняется, бейдж = 0 (поведение
  `track` без `apiClient` определено в `active-jobs-store.md`).
- **Пустой ответ** (`[]`) — бейдж скрыт, список пуст; не ошибка.

## Acceptance Criteria

- [ ] `GET /api/v1/active-jobs` отдаёт `pending` + `running` jobs в форме
      `JobResponse`; покрыт unit‑тестом хендлера и обновлённым sidecar‑контрактом.
- [ ] `JobRepo::list_active` реализован в SQLite‑адаптере и в `FakeJobRepo`.
- [ ] После закрытия приложения во время транскрипции **или** генерации протокола
      и повторного запуска встреча подсвечена в сайдбаре как «в работе».
- [ ] При открытии такой встречи виден `PipelineProgress` с процентом и
      подстадией (после подтягивания живого прогресса).
- [ ] Счётчик активных jobs в сайдбаре корректен и скрывается при 0.
- [ ] Клик по счётчику открывает список встреч в работе; клик по встрече ведёт на
      её детали.
- [ ] Повторный засев не плодит второй `JobPoller` на тот же job.

## Implementation Phases

1. **Бэкенд.** `JobRepo::list_active` (порт + SQLite + fake), хендлер
   `jobs::active`, маршрут в `api_routes`, тесты (хендлер + sidecar‑контракт +
   список маршрутов router’а).
2. **Засев QML.** При `api.configured` запросить `active-jobs` и прогнать через
   `ActiveJobsStore.track(...)`; обеспечить идемпотентность.
3. **Сайдбар.** Счётчик `activeCount()`; список встреч в работе по клику;
   навигация на детали.
4. **Проверка.** Сценарии: рестарт во время transcribe; рестарт во время
   protocol; несколько активных jobs одновременно; удаление встречи с активным
   job; запуск с несконфигурированным `api`.
